Exactly what each flag controls

Cross-computer collaboration

Pair computers, synchronize shared folders, and send messages across computers.

  • Today: Currently shares the inbox capability; needs its own gate.
  • Behavior when disabled: Keep local inboxes, tasks, and local agent messages available.
  • Enforcement points: Collaboration settings; /collaboration/*; /api/v1/collaboration/*; service initialization, sync worker and remote dispatch.

Skill kits

Register, install, inspect, and uninstall project skill kits.

  • Today: The existing Harnesses settings screen uses /harnesses/*; it has no separate edition gate.
  • Behavior when disabled: Leave installed files intact. Turning the flag off does not uninstall anything.
  • Enforcement points: Harnesses menu/modal, /harnesses/* handlers, and any direct CLI entry points.

Harness management

DuckTerm-assisted installation and setup of agent CLIs.

  • Today: Agent setup now requires harness_management in both the dashboard and native Mac entry points.
  • Behavior when disabled: Keep launching, resuming, and using already-installed Claude/Codex sessions. Do not disable the core harnesses capability.
  • Enforcement points: Agent setup UI and native setup actions; discovery needed for ordinary launch remains available.

Bring your own API key

Use a personal provider key or custom API endpoint for DuckTerm AI features.

  • Today: AI settings and key routes exist; there is no independent release gate.
  • Behavior when disabled: Retain saved settings and Keychain keys. Keep harness-based AI configuration available. No silent provider switch when a stored API configuration is disabled.
  • Enforcement points: AI settings options, key verification/storage routes, and backend dispatch before any key access or API call.

Backup

Backup controls and operations require the backup flag. Local archives are supported without cloud storage. Cloud upload and sync additionally require BYOC and an eligible edition. Turning flags off retains all existing archives, destinations and credentials. The owner’s personal installation opts in.

Bring your own cloud

Remote cloud workspaces and the workflows that create, move, or continue work there.

  • Today: Full has remote_workspaces; Lite/Code already omit it.
  • Behavior when disabled: Keep local clones and local terminals. Do not stop remote jobs or delete credentials, hosts, or saved projects.
  • Enforcement points: Remove remote_workspaces from effective capabilities when off; retain existing backend and native host admission checks. Audit cloud setup, transfer, backup, and connector entry points for shared use.
Two scope boundaries matter: cross-computer collaboration is separate from the local inbox; skill-kit management is separate from running an agent CLI. The current “Harnesses” menu manages skill kits, so its name must not cause us to disable normal local agents.

Features retained by owner decision

The owner decided to keep folder-chat message sending, Change harness, Merge back / Merge with agent, and automatic approval available. Do not add the four additional default-off flags suggested during review. Checkpointing and memory also remain enabled. Reliable checkpointing is a release requirement for the workflows that depend on it.

Required evidence includes successful summary generation and review, a saved revision that can be reopened with its evidence, correct incremental record selection, accurate progress and completion status, and successful use of that saved memory during a harness switch or agent merge. Existing confirmation, permission and safety checks still apply.

The six default-off flags above remain the agreed release direction. All six remain enabled on the owner's personal installation through local overrides.

Existing operational switches

DUCKTERM_ORACLE=off, DUCKTERM_SUMMARIZER=off, and DUCKTERM_RELEASE_CHECK=off already control particular background behavior. They are not a unified release-flag system. Legacy summarizer command/URL settings have their own precedence, so “summarizer off” must not be treated as a general network kill switch. Diagnostic, path, credential, and packaging environment variables are outside this feature list.

Implemented configuration and remaining release checks

  1. One registry: src/duckterm/release_features.py defines six stable IDs and names, default-off availability and BYOC edition eligibility. The app’s Feature flags page reads the server-generated inventory. This document records scope and release policy.
  2. One local configuration: Use feature-flags.json under the selected app instance’s home, with the format {"flags": {"backup": true}}. Omitted flags are off. No database migration, remote flag service, or account requirement. Missing configuration uses release defaults. Invalid configuration leaves experimental features disabled and reports the problem.
  3. One effective snapshot: resolve edition eligibility and flags together at server startup. Advertise the resulting capabilities to the dashboard and native Mac app. Flags are availability controls; existing authentication and permission checks remain mandatory.
  4. Inspect before changing: add a read-only “Feature flags” page in Settings with the flag, release default, effective value, reason (default, local override, or edition unavailable), and restart requirement. A later explicit owner change can write overrides; the inventory page itself does not activate features.
  5. Enforce at execution: block disabled routes before handlers, do not start disabled background workers, and gate native setup/cloud operations. Existing settings and keys remain stored. A disabled saved API backend reports why it is unavailable rather than silently sending work to a different provider.
  6. Preserve existing work: disabling a flag never deletes a session, summary, key, skill kit, host, or project. Existing personal use must be handled with explicit overrides before installation, not inferred from hostname or account identity. Disabling cloud access may hide controls while remote processes continue; show that clearly in the flag description.
  7. Website consistency: keep all three downloads available, but list only enabled features as generally available. Label gated capabilities experimental/opt-in, with no promise that a flag bypasses edition eligibility. Website copy should use the release inventory rather than a separate hand-maintained feature matrix.

Before a new feature ships

Release-dev should ask: “Does this new feature need a default-off feature flag before shipping?” The release record must answer that question and link the test evidence. Being merged is not evidence that a feature is ready to enable for everyone.

  1. Identify the feature owner, affected editions, flag decision and public default.
  2. Test both off and on states, including direct API calls, native Mac entry points, background workers, and local versus remote paths.
  3. Verify that default-off builds preserve local sessions, inboxes, checkpoints and existing saved data, and make no disabled-feature side effects.
  4. Test missing, invalid and old flag configuration; ensure an override never unlocks an edition-excluded capability.
  5. Build fresh Lite, Code and Full candidates without personal overrides. Check the effective flag inventory in each actual Mac app, not only the browser.
  6. Obtain owner review for visible changes and a deliberate decision to enable an experimental feature by default. Update the website and release notes to match the shipped state.

First implementation acceptance checks

  • Cross-computer off: no pairing, remote dispatch or synchronization; local inbox still works.
  • Skill kits and harness management off: setup controls and corresponding actions unavailable; existing local Claude/Codex sessions still launch and resume.
  • BYOK off: neither saved keys nor environment keys can cause a provider API call through the disabled feature; stored keys remain untouched.
  • BYOC off: remote transfer and host launch refused by backend and native UI; local cloning works; remote work and saved host records remain intact.
  • Read-only inventory lists every flag and the reason for its effective state; no secret values appear.
